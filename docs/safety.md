# Safety

- Loopback bind only (`CALAB_BIND` is the explicit opt-in the container uses); the compose file publishes `127.0.0.1` only (a test pins it). The container runs as a non-root user, read-only, with every capability dropped.
- Host header must be a loopback name; writes must be same-origin.
- Netguard blocks every outbound connection (fetch, socket, DNS, UDP) with a self-test, and a test asserts zero attempts in the server process across the whole API in Mock. There is no worker thread and no child process. Every URL in a mock hop is a `.example` host and is never sent. The one exception is Live (step 3): `index.js` calls `allowHost()` for the single PingOne authorization host, and only when the PingOne settings are valid and no guard refuses (a lab with no settings, `CAL_ALLOW_LIVE=0` or a refusing guard allows nothing); fetch, socket and DNS lookup then accept that exact name, while UDP, the resolver functions and every other host stay refused and recorded.
- **No field takes a credential.** A body with an unknown key is refused (without naming the key). Mock tokens are labelled MOCK and signed with a public mock key (built with `createECDH` + `createPrivateKey`); they protect nothing. **Live (step 3) is the one place a credential exists:** the worker client secret is read from the owner's shared settings file by `settings.js` (`util.parseEnv`, four keys), never copied into `process.env`, held in a closure in `live.js`, sent only in the Authorization header of the token call, shown in a hop as write-only, and never returned, logged or stored (a test searches every answer, the history and the run for it). The live token is shown masked (first 6, last 4) with its decoded header and claims. Masking is a heuristic; the real protection is that the secret and the raw token never enter a response object.
- **Mock sign-in (rule 11).** A mock run needs `IDP` unset (the default: each mode uses its own IdP) or `mock`, AND `ALLOW_MOCK_SIGNIN=1`, and is refused behind a proxy (forwarded headers) or on a non-loopback bind (Docker is the one exception: its compose file publishes on the Mac's `127.0.0.1` alone and says so with `CAL_PUBLISH=loopback`). `NODE_ENV=production` is not a guard: the Docker image sets it.
- **Live mode (Real)** can be selected with the toggle whenever the PingOne settings are complete (owner 2026-11-10, option a: rule 19 "Real if configured"), unless `CAL_ALLOW_LIVE=0` (the lab-invented OFF switch), `IDP` is pinned to `mock` (or anything but `pingone`), there is a proxy header, or the bind is not loopback (Docker's loopback-only publish counts). With no settings the Real button is disabled with a how-to naming the missing `PINGONE_*` and `POST /api/mode` answers 409. **Real works in Docker from the app's .env:** compose passes only the four `PINGONE_*` names (and the off switch) by `${VAR:-}` substitution, never `env_file`; the server takes them from its environment once at startup (`CAL_LIVE_FROM_ENV=1`, pinned in compose; a host run ignores shell `PINGONE_*`) and deletes them from `process.env` before anything else runs. The value is still visible to whoever can run `docker inspect` on the owner's own Mac, as any compose environment value is. The hosted build refuses Real entirely. `CAL_LAB_MODE=live` makes new workspaces open showing live without checking these; every live run still checks them and gets 403 until they hold. When they hold, a live run makes two calls (the public discovery document and a client-credentials token) to the one configured PingOne environment through `live.js`: https (http only to a loopback fake), a fixed path under `/<environment id>/as/`, no redirect followed, 8 s timeout, 64 KB cap, `assertAllowed()` before every call, two runs in flight at most. A run in live never signs a customer in, so the mock sign-in guard (rule 11) is not involved and no mock hop is mixed in. VERIFIED against a real PingOne environment by the owner on 2026-11-05 (LIVE_OK and the LIVE_REFUSED bad-secret path).
- **Nothing the visitor types is echoed.** Ids in the path (use case, vertical, persona, mode) are looked up in fixed lists and answered with fixed text; the workspace id must match `[a-z0-9-]{1,40}` and not look like a credential; unknown body keys are refused without naming them; every JSON answer is masked again by the specific credential detectors, except the MOCK tokens the lab minted for that answer (rule 4: tokens are shown raw). Masking is a heuristic: not every secret has a recognisable shape.
- Every user-supplied value used as an object key or lookup is checked with a type test and `Object.hasOwn` (or a `Map`); `__proto__`, `constructor` and `prototype` are refused.
- Honest status codes: 400 bad input, 403 a guard or a policy, 404 unknown use case, 409 workspace full, 429 too many workspaces or two live runs in flight, 501 a stub vertical, 503 live asked for but the PingOne settings are missing or invalid.
- Writes are serialised per workspace (a promise chain) and capped: 100 runs per workspace (a full workspace refuses the next run with 409 until Reset), 500 workspaces (new ones refused at the cap, nothing is evicted), idle for an hour expires.
- The server writes no file. The one settings read is the app's own optional `.env` beside `docker-compose.yml` (resolved from the repo root; `CAL_ENV_FILE` for tests) with `util.parseEnv`, taking `CAL_LAB_MODE`, `LAB_ALLOWED_HOSTS` and `SHELF_URL` (into the environment, the shell wins) and the four `PINGONE_*` live keys (to `live.js` only). A bare `MODE` in it is ignored, and so are the guard keys (`CAL_ALLOW_LIVE`, `IDP`, `ALLOW_MOCK_SIGNIN`) on a host run. In Docker, compose fills the four `PINGONE_*` and `CAL_ALLOW_LIVE` from it by name (substitution, not `env_file`); `CAL_ALLOW_LIVE` can only turn Real off.
- Only `.example` and `.invalid` hosts appear in any shipped text (a doctor check scans the filled story and the manifest in every vertical).
- The source catalog (AI-DEMO2) is read once by `scripts/gen-manifest.mjs`; the app reads only the committed `data/usecases.json`.
